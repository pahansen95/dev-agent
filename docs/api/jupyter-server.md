# Jupyter Server Management Research Summary

This research investigates embedding Jupyter Server in various execution contexts, focusing on performance and lifecycle management. The study developed patterns for running Jupyter ServerApp as background threads, subprocesses, and inline processes.

**Key Findings:**

- **Security:** For local deployments, bind to localhost, use authentication tokens, disable unnecessary services, maintain CORS restrictions, and run as non-root.

- **Asyncio Integration:** Run Jupyter Server in separate threads to prevent event loop conflicts and deadlocks. Jupyter Server uses Tornado which relies on Python's asyncio.

- **Long-Running Sessions:** Default settings (no idle culling) work well for persistent sessions. If enabling culling, carefully configure timeout parameters to prevent disruption.

The research methodology included configuration testing, implementation of three embedding patterns, REST API load testing, and security review. Deliverables include automation scripts, performance analysis, an embedding guide with best practices, and risk mitigation strategies.

Primary risks include port collisions, thread deadlocks, authentication misconfiguration, and resource leaks - all with documented mitigation approaches. The implementation follows a four-week development schedule from setup through documentation.

Programmatic Jupyter Server Management – Research Report

Objectives
	•	Embed Jupyter Server in Various Contexts: Develop reproducible patterns to run a Jupyter ServerApp in different execution contexts – in a background thread, as a separate subprocess, and inline within a process. Each pattern should be demonstrated with working code and allow clean startup and shutdown.
	•	Performance Benchmarking: Measure and benchmark the server’s performance in each scenario, including startup time, baseline idle resource usage (memory/CPU), and additional overhead for launching kernels. This involves timing how long the server takes to start serving, how much memory it consumes at idle, and the latency introduced when starting a new kernel.
	•	Lifecycle Management via APIs: Validate that Jupyter Server can be controlled through both its REST HTTP API and its Python API. This includes using REST endpoints (e.g. the shutdown endpoint) and Python methods (e.g. ServerApp.stop()) to manage the server and kernels during normal operation, under load, and for graceful shutdown, ensuring no resources (such as kernel processes or ports) are left hanging.

Key Questions

1. Reducing the Attack Surface in Local-Only Mode

When running Jupyter Server on a single machine (no remote access needed), several configuration flags can minimize the attack surface:
	•	Bind to localhost: By default, the server listens only on the loopback interface (ServerApp.ip = 'localhost') and forbids off-host hostnames. In Jupyter Server, allow_remote_access is False by default, meaning any HTTP request whose Host header is not local is rejected ￼. This protects against DNS rebinding attacks, ensuring that only clients connecting via localhost (or configured local hostnames) are served ￼. Keeping allow_remote_access=False (the default) is important for local-only deployments.
	•	Disable Browser Auto-Open: Launching Jupyter without a browser can reduce exposure. Using the --no-browser flag (which sets ServerApp.open_browser = False) prevents the server from automatically opening a browser upon start. This is mainly a convenience setting, but it avoids creating a redirect file on disk or exposing the authentication token via command-line. (By default in Jupyter Server, open_browser is already false ￼.)
	•	Authentication Token or Password: Jupyter Server normally requires an auth token (a random secret URL parameter) for the web interface. In local-only scenarios, some users disable token auth for convenience (by setting an empty token). However, leaving the server completely unsecured is dangerous if any other user or process on the machine can access the HTTP port. It’s recommended to keep authentication enabled even on localhost. By default, Jupyter Server 2.x uses a token-based login unless a password is configured, and will print the token in the console if --no-browser is used. If you do choose to disable the token (for a fully internal service), ensure the server still isn’t accessible to untrusted users. For example, one might run with --ServerApp.token='' only if behind other protections (like 100% private network). Generally, the default behavior (random token) is a good security measure for local mode.
	•	Disable Unneeded Services: Minimizing what the server offers can shrink potential attack surface. For instance, you can disable the terminals feature (ServerApp.terminals_enabled = False) if shell access through Jupyter is not required. Note that the Jupyter docs caution this doesn’t truly make the system more secure by itself (anything a user can do in a terminal, they could also do in a notebook) ￼. Still, disabling terminals removes one UI vector and the dependency on the terminado package, which could reduce exposure to any vulnerabilities in those components. Likewise, if you are not using JupyterLab or any server extensions, you might refrain from enabling them.
	•	Cross-Origin and Cross-Site Protections: Keep the default CORS settings unless needed otherwise. By default, ServerApp.allow_origin is empty (no arbitrary origins allowed) and allow_origin_pat is empty as well, so the server will not permit cross-site API requests unless explicitly configured ￼. Only same-origin or explicitly allowed origins can access the REST API. Similarly, allow_credentials is False by default (not setting Access-Control-Allow-Credentials) ￼. These defaults mean a malicious website can’t easily craft AJAX calls to your local Jupyter Server (the browser will block them due to CORS). For a local-only server, you typically do not need to set --ServerApp.allow_origin=* (which would allow any website to interact) – leaving it restricted is safer.
	•	Unauthenticated Endpoints: Jupyter Server has a setting allow_unauthenticated_access (default True in 2.0) which controls whether endpoints that don’t have an explicit authentication decorator can be accessed without logging in ￼. With the default True, certain benign endpoints (like the server version check at /api which has no auth required) will respond without auth ￼. If you want to lock down absolutely everything, you could set ServerApp.allow_unauthenticated_access = False to require authentication on all routes (except those explicitly marked as safe) ￼. This is a stricter mode that might be considered if the environment demands it.
	•	Run as Non-Root: Ensure allow_root remains False (it is False by default) ￼ so that you don’t accidentally run the server with root privileges. Running Jupyter as root is not recommended since any compromise of the process would yield full system access. In local-only usage, there’s rarely a need to run as root; if port 80 or 443 is not needed (Jupyter typically runs on 8888 by default), there’s no reason to elevate privileges.

In summary, for a local-only server, use the defaults (which already bind to localhost and require a token) and avoid turning on any option that broadens access. If anything, you can further narrow access by disabling unused functionalities (terminals, extensions) and tightening auth rules. These configurations collectively ensure the server only listens locally and only serves authenticated requests, significantly reducing the reachable attack surface from other processes or browsers ￼ ￼.

2. Tornado IOLoop and Asyncio Integration in Embedded Servers

Jupyter Server is built on Tornado, which since version 5+ uses Python’s asyncio under the hood for its event loop. This means that Tornado’s IOLoop is now a wrapper around the asyncio event loop ￼ ￼. This has important implications when embedding Jupyter Server into an application, especially if your application (or environment) is already running an asyncio event loop.

In a typical standalone launch (e.g. running jupyter server from the command line), Jupyter will start Tornado’s I/O loop to handle requests. If you attempt to start the server in the same thread as an already-running asyncio loop, you’ll encounter errors or hang-ups. This is because you would essentially be trying to start a second event loop in a thread that already has one running. As one Jupyter developer explained when this issue arose, “the event loop is already running, because Tornado now runs on top of asyncio” ￼. In practice, this situation often comes up if, say, you try to launch a Jupyter Server inside an existing Jupyter notebook or inside an asyncio-based application – the main thread’s loop is active, and Tornado cannot simply start another.

How to embed properly? The key is to run the Jupyter Server’s IOLoop in a separate thread or context so it doesn’t clash with the main asyncio loop. Python’s default asyncio policy provides one event loop per thread ￼. Therefore, by launching the Tornado server on a background thread, you ensure it gets its own independent event loop (separate from the main thread’s loop). This approach is commonly used to embed Tornado servers in applications that are themselves running asyncio or other loops. In such an embedding:
	•	You create a new thread and within that thread, start the Jupyter ServerApp. For example, one might do:

import threading
from jupyter_server.serverapp import ServerApp

def run_server():
    app = ServerApp()
    app.initialize(["--no-browser", "--port=0"])  # example args
    app.start()  # This will start the IOLoop and block this thread

thread = threading.Thread(target=run_server, daemon=True)
thread.start()

In this pseudocode, the server runs on a separate thread, so it can start Tornado’s IOLoop without interference. The main program can continue doing other work (or running its own loop).

	•	Under the hood, Tornado will call asyncio.new_event_loop() for that thread and set it as current. The server’s Tornado IOLoop then runs forever (until stopped) on that thread. Because the main thread’s loop is separate, there’s no conflict. This pattern is confirmed by the fact that asyncio’s default policy ties event loops to threads – a new thread means a new event loop that can run concurrently ￼.
	•	If running the server inline (in the same process) without a separate thread, you must be careful. You can integrate Jupyter’s Tornado app into an existing asyncio loop, but it requires advanced handling (using Tornado’s .add_callback or asyncio loop add_reader, etc.). A simpler approach is to avoid this complexity by always isolating the server’s loop to its own thread or subprocess.

In summary, Tornado’s IOLoop and asyncio will coexist fine as long as you don’t try to drive two event loops in one thread. For embedded contexts, the rule “one loop per thread” is vital. By moving the Jupyter Server to a dedicated thread (or separate process), you let Tornado use asyncio normally in that thread. The main application can interact with the server via REST calls or other thread-safe mechanisms (for example, sending an HTTP request to the server’s REST API, or using thread-safe callbacks to stop it). This approach prevents deadlocks and “event loop already running” runtime errors. We will use this pattern for the thread-based and in-process embedding scenarios to ensure smooth integration.

3. Idle Kernel Culling and Long-Lived Sessions

Jupyter Server provides configurable culling of idle kernels – i.e. automatically shutting down kernel processes that have been idle for some time – via the MappingKernelManager.cull_idle_timeout setting. The implication for long-lived kernel sessions is that if this timeout is set, a kernel that isn’t actively used could be terminated automatically, which may be undesirable for services that need to maintain state over long periods.

Important points about idle culling:
	•	By default, idle culling is disabled. The default value of cull_idle_timeout is 0 (zero), which means “no culling” ￼. In this default configuration, a kernel will run indefinitely regardless of inactivity. For a service that requires long-lived kernels (e.g. a persistent background computation or a long-running notebook session), the default of no timeout is safe – kernels won’t be culled just for being idle.
	•	If an administrator enables culling (by setting a positive cull_idle_timeout in seconds), the server will periodically check for idle kernels and shut them down once their idle time exceeds the threshold ￼. “Idle” in this context typically means no execution activity and no API activity from any client for that duration.
	•	There are additional flags that refine what “idle” means:
	•	cull_connected: By default this is False ￼, meaning do not cull kernels that have an open connection (e.g. a user still has a notebook open in a browser connected to the kernel). If cull_connected were True, even kernels with active WebSocket connections (open notebooks or consoles) could be culled if idle. For long-lived interactive sessions, you’d want cull_connected=False so that as long as a client is connected, the kernel stays (this is the default behavior).
	•	cull_busy: Default False as well ￼, meaning do not cull kernels that are actively busy executing code. Typically a busy kernel isn’t “idle” anyway, but this flag covers the case where a kernel might be stuck or long-running – with cull_busy=False it will not be culled no matter how long it runs a task.
	•	cull_interval: This sets how frequently the server checks for idle kernels (default 300 seconds) ￼. A shorter interval means the culler reacts faster but also means a slight overhead more frequently.
	•	For a service that must maintain long-lived kernel sessions, the safest approach is to disable idle culling entirely (ensure cull_idle_timeout = 0, which is already the default) ￼. This guarantees the server will not arbitrarily shut down kernels due to inactivity. If some form of culling is required (for example, to conserve resources in a multi-user environment when notebooks are abandoned), you would need to set the timeout high enough that expected use cases are not impacted, and keep cull_connected=False so that any kernel which is still associated with an open client is preserved. In practice, JupyterHub deployments often set timeouts on the order of tens of minutes or hours, but for a dedicated service where kernels are precious, you might choose no culling.
	•	Another setting of note is ServerApp.shutdown_no_activity_timeout. This is a timeout to shut down the entire server after a period of total inactivity (no kernels running and no API activity) ￼. By default it is 0 (disabled). If you were to set this in a service, it would stop the whole server after, say, an hour of nobody using it. For long-lived services, you’d likely leave this off as well, to avoid the server stopping itself. (It’s more useful in ephemeral notebook scenarios or on-demand setups.)

In summary, the default Jupyter Server behavior will not cull idle kernels at all, which is suitable for long-lived sessions. If culling is enabled, it must be tuned carefully. For a service needing long-lived kernels, one should either not enable culling or ensure that any kernel with an attached session (client) is exempt (cull_connected=False) and use a sufficiently large timeout. Otherwise, users might find their session gone if they pause activity for too long, which could be disruptive. Always align the cull_idle_timeout with the expected interaction pattern of your service (e.g. if users might idle overnight, the timeout must exceed that or be disabled).

Methodology

To achieve the objectives and answer the questions above, we will undertake a systematic series of experiments and analyses. The methodology consists of the following steps:
	1.	Configuration Sweep and Startup Analysis: We will run the Jupyter Server with various configuration flags to observe their effects on startup time and resource usage. Key flags include --no-browser, authentication toggles, and port settings:
	•	Start the server with and without auto-opening a browser, with and without requiring token authentication (explicitly disabling the token for testing), and on specified ports vs. ephemeral ports.
	•	Measure the startup latency in each case. For example, measure time from process launch to when the HTTP server is accepting connections. We hypothesize that most flags have minimal impact on startup time, but certain scenarios (like a port conflict causing retries) can introduce delays.
	•	The port configuration will be tested by forcing collisions: if we set a fixed port that’s already in use, Jupyter Server will try the next ports (up to port_retries=50 by default) ￼. We’ll log how much extra time that adds per retry. If using port=0 (let the OS pick an open port) it should be quick to start since it avoids collisions altogether.
	•	We will also observe idle resource usage in each config (using tools like psutil to record memory RSS and CPU % after startup). For example, does disabling certain components (like turning off terminals or not loading extensions) reduce memory footprint? We’ll document these differences if any.
	2.	Embedding Patterns Implementation: Develop three small harnesses to run Jupyter Server:
	•	Thread-Based: Launch ServerApp in a Python thread (within the same process). This will test the ability to start and stop the server from a controlling program. We’ll ensure to use the pattern of one IOLoop per thread as discussed. After starting the thread, the main thread can interact via REST calls. We will call ServerApp.stop() from the main thread (or via an IOLoop.add_callback into the server’s thread) to initiate shutdown, and verify the thread exits cleanly.
	•	Subprocess: Launch Jupyter Server as a separate process (e.g. using subprocess.Popen(["jupyter", "server", "--no-browser", "--port=..."])). This mimics how one might programmatically start a server as a child process. We will communicate with it via HTTP (for example, use the REST API to check it’s up, maybe automate a few actions, then shut it down). Shutdown in this scenario can be done by sending an API request to /api/shutdown or simply terminating the process. We prefer the graceful API route to let it cleanup (which under the hood calls ServerApp.shutdown_server logic, issuing a SIGTERM if necessary after a timeout) ￼.
	•	Inline/In-Process: Run Jupyter Server in the main thread of a process (similar to how one normally runs it, but we will do it via a script or interactive session). In this scenario, because app.start() will block, we might not be able to do much else in that same process. We will handle this by either running it for a short duration or using signals. For testing, we can simulate an inline run by launching the server in the foreground, then from an external script sending it a shutdown request after a delay. This will test that even in inline mode, a clean shutdown can be achieved via the REST API. (Alternatively, we could explore running the Tornado IOLoop in an asyncio-friendly way without a separate thread – but as noted, that requires careful integration. The simpler approach is to treat inline mode as just a normal blocking run and control it externally.)
For each embedding approach, we will verify that the server starts and stops cleanly. “Cleanly” means:
	•	The HTTP endpoints become available and responsive after start.
	•	After stopping, the server’s port is freed (no process is still listening) and all kernel subprocesses are terminated. We should see no orphaned python kernel processes in the process list.
	•	No zombie threads or lingering file handles. For the thread case, we’ll join the thread to confirm it exits. For subprocess, ensure the child process is gone. We will use logging and OS tools to confirm resources are freed.
	3.	REST API Load Testing: Using a tool like wrk (an HTTP benchmarking tool) or a custom Python asyncio client, we will stress-test the Jupyter Server’s HTTP API. The goal is to measure how the server performs under load, especially while managing multiple kernels:
	•	We will simulate heavy usage of endpoints such as kernel management APIs. For example, sending concurrent requests to start new kernels (POST /api/kernels), list kernels (GET /api/kernels), and possibly stop kernels (DELETE /api/kernels/{id}), as well as standard notebook actions like listing contents (GET /api/contents).
	•	We plan to vary the number of simultaneous clients (connections) and the number of active kernels to see how performance scales. For instance, measure the average response time of listing all kernels when there are 2, 10, 50 kernels running.
	•	We will log response times (latencies) and throughput (requests per second). If using wrk, it can report metrics like latency distribution and requests/sec. If using a Python approach (aiohttp), we can gather timings for each request and compute statistics.
	•	One specific test will be plotting requests/sec vs. kernel count: we will incrementally increase the number of running kernels in the server (by starting new ones) and at each step measure the throughput of a particular endpoint (say, hitting a trivial endpoint or the kernels list). This will produce a curve of how performance degrades as more kernels are managed. We expect some degradation as each kernel consumes resources, but the server should handle dozens of idle kernels easily. We’ll capture if any particular threshold causes a sharp drop (for example, if CPU becomes saturated handling many kernel heartbeats or I/O).
	•	During load tests, we’ll also monitor resource usage to see if there are any memory leaks or buildup. For example, if we create and destroy 100 kernels in succession, does the memory return to the baseline or creep upward? This can indicate if any objects aren’t being freed properly.
	4.	API and Shutdown Behavior Under Load: We will specifically test the server’s ability to handle lifecycle operations during heavy load:
	•	While the server is busy (e.g. multiple requests in flight, and several kernels doing work), issue a shutdown command via the REST API (POST /api/shutdown which should gracefully stop the server). Verify that the server indeed shuts down after completing ongoing requests. This tests graceful shutdown: the server should stop accepting new connections, allow in-progress operations to finish (or time them out), terminate kernels, and exit. We will check the logs to see that it goes through the expected shutdown sequence (shutting down kernels, cleaning up, etc.).
	•	Similarly, test the Python API call ServerApp.stop(). In the thread-based embedding scenario, we can call app.stop() from the main thread. We need to ensure this doesn’t deadlock. (If calling from outside the server’s thread, it may need to marshal to the server thread’s IOLoop internally – we’ll confirm if ServerApp.stop() is thread-safe or if we should instead call it via an IOLoop.call_later on the server’s loop.) The expectation is that stop() will initiate the same shutdown process as the REST call. We’ll verify that this method works reliably even if the server is under load.
	•	We will also test other lifecycle-related REST endpoints, such as shutting down individual kernels (DELETE /api/kernels/{id}) while the kernels are busy or idle, and see that the server and client handle it properly (the kernel process should exit, and the server no longer lists it).
	•	Error handling will be observed: for example, if we try to shut down a kernel that is already dead, does the server gracefully handle the request with a proper error? If we flood the server with too many requests, does it slow down linearly or become unresponsive? These are aspects to record.
	5.	Security and Configuration Review: Aside from empirical testing, we will conduct a static review of Jupyter Server’s configuration and logs to identify any potential security issues or misconfigurations:
	•	Headers and CORS: Confirm that with default settings, the HTTP responses include the expected security headers. For instance, check that no Access-Control-Allow-Origin: * is present unless we explicitly allow it. We’ll also verify that the Content-Security-Policy and other headers Jupyter may set are present (Jupyter Notebook/Lab often sets CSP for notebook if running under certain conditions).
	•	Authentication Enforcement: We will attempt some requests without providing the token to ensure the server indeed blocks them (expects a token or auth cookie). This is to validate that our attack surface is indeed minimized. For example, an HTTP 403 or 401 should be received when trying to access a notebook or kernels list without a token in a local scenario.
	•	Open Ports: Using tools like netstat, we will confirm that the server is only listening on the intended interface/port (e.g. 127.0.0.1:8888 by default). Also, check if any other ports are opened by side services. Jupyter Server itself should only need one HTTP(S) port. Kernels communicate over ZMQ ports, but those are not listening globally by default (they are on localhost interface as well, and kernel ports are randomly allocated). We’ll verify that no unexpected listener is open.
	•	Idle Culling Settings: If possible, test the culling mechanism in a controlled way: enable a short cull_idle_timeout (like 60 seconds) and see that an idle kernel is culled, and that a kernel with an open notebook (connection) is not culled when cull_connected=False. This ensures we understand the behavior. Then we will disable it for long-running tests to avoid interference.
	•	Leak checks: After all tests, we will inspect for any “leaks” or leftover resources:
	•	Ensure all kernel processes have ended.
	•	Ensure that repeated start/stop cycles of the server do not consume increasing memory over time (which could indicate a memory leak in the server).
	•	Use Python’s garbage collector or tracemalloc in a test scenario if needed to see if objects like kernel managers are freed on stop.
	•	We will maintain a risk log of any potential issues found (e.g., “After 50 rapid kernel restarts, one kernel process remained – indicates a possible cleanup race condition” or “High memory usage when 100 kernels are idle – possibly due to per-kernel overhead”). Each issue will include a mitigation or next step (for example, adjust configuration or file a bug if needed).

Throughout this methodology, all findings will be documented. The use of official documentation (like config options from Jupyter Server’s docs) will guide our configuration choices and interpretation of results. We will link relevant parts of the docs in our final report to justify configurations and to provide context (for instance, referencing the default values for culling or the purpose of certain security settings). This ensures our approach is transparent and reproducible.

Risk Mitigation Strategies

Throughout the project, we will keep an eye on potential risks and implement mitigations proactively:
	•	Port Collisions and Binding Issues: Using the default port=0 (random open port) for most tests will avoid collisions when running multiple instances of the server ￼. In cases where we need a fixed port (to test the port retry logic or to simulate a user scenario), we will handle exceptions where the port is in use by catching the error or relying on Jupyter’s built-in retries. The server’s default of 50 retries means it will try the next 50 ports if the first choice is taken ￼, but this could slow down startup significantly if many are occupied. Mitigation: in a test environment where we intentionally cause a collision, we might lower ServerApp.port_retries to 1 or 2 to fail fast and measure that scenario, rather than waiting through 50 attempts. Additionally, after each test we’ll ensure the server processes have terminated and released the port, to not cascade port conflicts into subsequent tests.
	•	Thread Deadlocks or Concurrency Issues: Running the server in a separate thread introduces concurrency considerations. To prevent deadlocks, we will avoid calling any blocking server methods from the wrong thread. For example, if we need to stop the server from the main thread, and if we determine that ServerApp.stop() is not safe to call across threads directly, we will use the server’s I/O loop to schedule the stop. A pattern might be: server_app.io_loop.add_callback(server_app.stop), which ensures the stop is executed in the server’s own thread. This avoids the main thread trying to manipulate Tornado state directly. We will document and use this approach if needed. We also mark the server thread as daemon so that if the main program exits unexpectedly, it won’t hang the entire process (though in normal operation we will cleanly join it). By isolating interactions to REST API calls (which are naturally thread-safe, since they go over HTTP) and using proper thread synchronization for any direct Python calls, we mitigate the risk of deadlocks. We’ll test these mechanisms early (Week 1–2) by starting and stopping the server repeatedly in an automated loop to ensure no hangs occur.
	•	Authentication Misconfiguration: A potential risk is accidentally leaving the server insecure during tests (for instance, disabling the token and forgetting to restrict access). To mitigate this, all tests on a single machine will still run with allow_remote_access=False so even if the token is disabled for a particular test, only localhost connections are allowed ￼. We will not test a no-token scenario on an interface other than loopback. When testing with authentication on, we’ll use the provided token in our HTTP client calls. We’ll also test that unauthorized requests fail, to confirm our understanding of the security model. Essentially, we treat the token like a password and manage it securely in our test scripts (it will be printed by the server on startup; our harness can capture it from stdout). By being conscious of these settings, we avoid a situation where, for example, a stray Jupyter server is left running without auth on an open network interface. In documentation, we will clearly warn about the dangers of misconfiguring auth, and recommend to never disable auth on a non-local interface.
	•	Resource Leaks (Kernels, File Descriptors, Memory): If our tests reveal that starting and stopping servers or kernels repeatedly causes resources to accumulate (e.g. each restart leaves an extra file handle open, or memory doesn’t fully return), we have mitigation strategies:
	•	For file descriptors, Jupyter Server has a setting min_open_files_limit which can raise the ulimit if needed ￼. If we run extremely many kernels, we might approach the FD limit. We will monitor ulimit -n and ensure it’s high enough, or use that config to bump it on launch.
	•	If kernel processes stick around (zombie kernels), we will implement a cleanup routine in our test harness to kill any remaining processes by name after a test, to avoid interference with subsequent tests. This is a safety net while we investigate the cause.
	•	For memory, if we suspect a memory leak, one mitigation in a long-running service is to periodically restart the server. While not ideal, it’s a common practice if a leak cannot be easily fixed. We will note this in the risk log if applicable (e.g. “observed memory usage growth of ~10MB/hour; acceptable for now, but consider a daily restart or further profiling”).
	•	We will use tools (like Python’s tracemalloc or objgraph) in a debug session to pinpoint leaks if any. If a clear bug is found in Jupyter Server (for instance, an object not being freed), a mitigation could be to manually clear or delete it in a custom shutdown routine until an upstream fix is available.
	•	Performance Variability: Benchmarking can be prone to noise (other processes on the system, etc.). To mitigate this, we will run tests multiple times and use averages, and where possible use a dedicated machine or container with consistent resources. We’ll also avoid running all tests in one long sequence without resets – for example, restart the server between major test scenarios to get consistent initial state.
	•	Documentation Accuracy: Since Jupyter Server is an evolving project (the docs we reference are for the latest version), we risk that our environment might differ slightly (especially if a newer version is released during our project). To mitigate confusion, we will lock the jupyter_server version we use (for instance, “using Jupyter Server 2.X for all tests”) and note it. We’ll ensure that the documentation references we cite correspond to that version (the official docs usually reflect the latest release). If any behavior is different, we’ll reconcile it (e.g. if a default changed, we’ll mention the version difference). This avoids misinterpreting config options.

By following the above strategies, we aim to minimize disruptions and ensure reliable results. Each risk is addressed either by configuration choices, additional tooling, or simply vigilance during testing. We will keep an audit trail of what was done so that if issues do arise, we can backtrack and identify when and why. Overall, this careful approach will help produce a robust and trustworthy research outcome, providing clear guidance on programmatically managing Jupyter Server.
